# PRD Agent V1.1 实现可行性评审

> 评审日期：2026-07-21  
> 评审对象：V1.1 产品需求与总体设计  
> 结论：有条件可行  
> 建议：按 M0 Agent Core、M1 Functional Product MVP、Production Profile 三层里程碑推进

## 1. 可行性结论

**可行性结论：有条件可行。**

**M0 Agent Core：可行性高。** 目标是验证 PRD Workflow、受控 Investigation Loop、仓库工具、Evidence、Grounding 和 Eval，不视为完成产品 MVP。

**M1 Functional Product MVP：可行性中高。** 包含基础 Web 工作台、人机确认、远程仓库快照和基础文档集成，但不承诺完整生产级恢复与多租户能力。

**Production Profile：可行性中。** 主要复杂度来自并发恢复、全链路幂等、权限隔离、外部副作用和运维。

## 2. 新增方案可行性矩阵

| 方案 | 可行性 | 主要依据 | 主要约束 |
| --- | --- | --- | --- |
| CLI 优先的最小 PRD Workflow | 高 | Python、Pydantic 和显式状态机足够支撑 | CLI 只是技术验证，不等于产品 MVP 完成 |
| LangGraph 主工作流与人机中断 | 高 | 原生支持 checkpoint、interrupt 和恢复 | 业务规则必须保持为独立纯函数，不能隐藏在图节点中 |
| Information Need 三级分类 | 高 | 分类输出结构简单且容易评测 | 必须定义清晰标注规范，否则 Precision/Recall 无意义 |
| 受控 Investigation Loop | 中高 | 有轮数、工具数、重复和无进展限制 | Coverage 模板和停止策略需要用 Eval 调整 |
| 本地代码库只读调查 | 高 | `rg`、文件读取和确定性 Parser 可完成首版 | 首版限定一种 Demo 技术栈和固定 commit |
| Symbol 与 Reference 工具 | 中 | 单语言 AST 或 Tree-sitter 可实现 | 跨语言和动态调用关系不能在首版承诺完整 |
| OpenAPI 与数据库 Schema Parser | 高 | 输入结构确定，适合确定性解析 | 只支持明确格式，拒绝把模型推测标为确定事实 |
| Evidence 与 Verified Fact | 高 | 数据边界明确，适合关系模型 | 必须控制代码片段大小、敏感信息和保留周期 |
| Source Grounding Checker | 中 | 可以组合确定性校验与模型判定 | 模型判定不能单独把 Fact 升级为 `SUPPORTED` |
| Document Quality Checker | 中高 | 规则、章节和验收覆盖可结构化检查 | 主观质量指标需要人工样本校准 |
| 固定 Eval、Baseline 与 Ablation | 高 | 对比配置和固定 Case 易于自动运行 | 10 个 Case 只适合回归，不足以支持强统计结论 |
| 历史 PRD 关键词检索 | 高 | 实现简单且可建立 Baseline | 召回结果不等于有效事实 |
| pgvector 混合检索 | 中高 | PostgreSQL 原生扩展成熟 | 应在关键词 Baseline 后通过 Ablation 决定是否加入 |
| Next.js + FastAPI 产品工作台 | 高 | 技术成熟，接口边界已定义 | 不能因 CLI 可用而从产品 MVP 中永久省略 |
| Redis + Celery + Outbox | 高 | 可支撑异步任务、重试和恢复 | 必须统一任务幂等与 Workflow 恢复责任 |
| GitHub/GitLab 远程调查 | 中高 | 只读 API 和固定 commit 可用 | API 搜索、目录和文件大小存在限制与速率约束 |
| 外部 Coding Agent Adapter | 中 | 可以统一输入输出 Schema | 黑盒行为、成本和来源精度必须通过对比评测 |
| 飞书创建与覆盖更新 | 高 | 业务流程和幂等边界清楚 | 授权、格式降级和写入限流需单独契约测试 |

## 3. 必须先收敛的架构决策

### 3.1 M0 Agent Core 不是产品 V1.1 MVP

PRD 要求前端任务列表、持续对话、状态恢复和 PRD 文档视图。总体设计又允许 Portfolio Core 只提供 CLI。这两者并非技术冲突，而是交付定义冲突。

建议拆成三个里程碑：

| 里程碑 | 定义 | 是否满足产品 PRD |
| --- | --- | --- |
| M0 Agent Core | 验证 PRD Workflow、受控 Investigation Loop、仓库工具、Evidence、Grounding 和 Eval | 否，只是技术验证 |
| M1 Functional Product MVP | 基础 Web 工作台、人机确认、远程仓库快照和基础文档集成 | 是，但不承诺完整生产级恢复与多租户能力 |
| Production Profile | 并发恢复、全链路幂等、权限隔离、外部副作用治理和运维 | 是，达到生产化基础 |

实施计划应把 Portfolio Core 改称“M0 Agent Core”，避免团队误以为完成 CLI 就已经完成 V1.1 产品目标。

### 3.2 统一使用 PostgreSQL

设计允许 Portfolio Core 使用 SQLite 或 PostgreSQL。该选择会影响 JSON 字段、部分唯一约束、并发锁、LangGraph Checkpointer 和后续迁移。

建议业务状态从 M0 开始统一使用本地 PostgreSQL，通过 Docker Compose 启动。CLI 仍然保持单命令入口，但不再维护 SQLite 与 PostgreSQL 两套行为。

SQLite 可以用于纯离线评测结果或单元测试，但不作为业务状态的第二套正式实现。

这一选择增加少量本地启动成本，但能避免 M1 重写持久化层，并与用户已确认的 PostgreSQL 技术栈一致。

### 3.3 明确选择 LangGraph

“LangGraph 或自定义显式状态机”会让实施计划无法锁定接口和恢复语义。

建议选择 LangGraph 的低层 Graph API 和 PostgreSQL Checkpointer，实现两个图：

- `PrdWorkflowGraph`：外层确定性主流程。
- `InvestigationGraph`：内层有界调查子图。

预算、重复检测、权限、Coverage 和状态迁移仍实现为普通 Python Policy，不使用高层通用 Agent 封装。

LangGraph 已提供 checkpoint、故障恢复和 human-in-the-loop interrupt，适合大纲、确认单元和最终确认节点。业务状态与图 checkpoint 分别管理，禁止把用户可见状态只保存在 checkpoint 中。

参考：[LangGraph Persistence](https://docs.langchain.com/oss/python/langgraph/persistence)、[LangGraph Interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

### 3.4 避免双重恢复系统

Production Profile 同时包含 LangGraph Checkpointer、Celery、Outbox 和业务状态表。若四者都尝试决定“从哪里恢复”，容易重复执行工具调用或生成节点。

建议责任划分：

- PostgreSQL 业务表：用户可见的产品状态和领域事实，是业务状态的唯一事实来源。
- LangGraph PostgreSQL Checkpointer：图节点状态和 interrupt cursor，只用于图执行与恢复。
- Outbox：在业务事务提交后发布“需要运行或恢复某个 Run”的命令。
- Celery：消息只携带 `run_id`，只负责唤醒和调度，不保存业务状态，也不自行推导下一节点。
- Redis：只作为 Broker、取消信号和短期事件，不作为恢复依据。

Worker 收到 `run_id` 后，从 PostgreSQL 读取业务状态并定位 LangGraph checkpoint，再按幂等规则恢复。Celery 官方文档明确提醒任务可能重复执行，因此所有外部调用都必须设置超时和有限重试。[Celery Tasks](https://docs.celeryq.dev/en/stable/userguide/tasks.html)

### 3.5 ID 映射、图版本、幂等键与 checkpoint 保留

ID 映射固定如下：

| ID | 含义 | 生成与关系 |
| --- | --- | --- |
| `task_id` | 用户可见 PRD 任务的领域聚合 ID | 创建任务时生成，任务生命周期内稳定 |
| `run_id` | 一次启动、继续或恢复命令的执行 ID | 每次调度生成；关联一个 `task_id`，是 Worker 幂等执行单元 |
| `thread_id` | LangGraph 持久化线程 ID | 按 `task_id + graph_name + graph_major_version` 确定，同一兼容图版本内稳定 |
| `checkpoint_id` | LangGraph 生成的图执行游标 | 关联 `thread_id`；只用于恢复和审计，不作为业务状态 ID |

每个任务和 Run 必须保存 `graph_name`、`graph_version`、`prompt_version` 与 `tool_schema_version`。运行中的任务固定使用创建时的图主版本；不兼容图升级不得直接读取旧 checkpoint，必须显式迁移或从已持久化业务状态重建新线程。

命令幂等键采用 `operation + task_id + expected_task_version + client_request_id`。工具调用使用 Action Signature；飞书等外部写入使用 `task_id + document_version + target_id`。幂等记录与业务变更应在同一 PostgreSQL 事务中提交。

checkpoint 默认保留策略如下：

- `RUNNING`、`WAITING_USER`、`RESUMING`：保留恢复所需的全部 checkpoint。
- `COMPLETED`、`STOPPED`、`FAILED`：保留确认边界、最终状态和最后失败点 30 天，其余中间 checkpoint 可异步清理。
- 删除任务：业务删除成功后清理对应 checkpoint；审计要求存在时只保留脱敏元数据。
- Eval：保留选定轨迹、配置和报告作为版本化评测资产，不与生产用户数据混用。

## 4. Investigation 实现建议

### 4.1 首版工具范围

M0 只实现以下核心工具：

1. `repo_tree`。
2. `search_text`。
3. `read_file`。
4. `parse_openapi`。
5. `parse_database_schema`。
6. `find_related_tests`。

`find_symbol` 和 `find_references` 可以在选定 Demo 技术栈后实现，不承诺跨语言完整性。Git 历史、事件消费者、Import Graph 和状态机解析保留在后续阶段。

### 4.2 Action 必须结构化

模型只能从 Tool Registry 中选择动作，并输出经过 Pydantic 校验的参数。系统拒绝任意 Shell、任意路径、任意网络访问和未注册工具。

Action Signature 应使用规范化 JSON，而不是简单字符串拼接：

```text
sha256(
  tool_id
  + canonical_json(arguments)
  + resolved_commit_sha
  + tool_schema_version
)
```

加入 `tool_schema_version` 可以避免工具参数语义升级后错误命中历史签名。

### 4.3 Coverage 采用模板，不让模型自由发明

Coverage 应按 Information Need 类型预定义。例如字段格式变更使用：

```text
api_contract
validation_logic
storage_schema
downstream_usage
tests
```

模型可以建议某项为 `NOT_REQUIRED`，但系统需要保存原因。Coverage 更新只能引用本轮新增 Evidence 或 Unknown。

### 4.4 默认预算可作为初值

文档中的默认值可用作初始工程参数：

```text
max_iterations = 5
max_tool_calls = 12
max_replans = 1
max_grounding_retries = 1
no_progress_limit = 2
same_action_limit = 1
```

这些值不应写死在图定义中，而应进入版本化的 `InvestigationPolicy`，并记录到每次 Evaluation Run。

## 5. Evidence、Fact 与 Grounding

### 5.1 数据分层是可行且必要的

V1.1 将 Tool Result、Evidence、Fact 和 PRD Claim 分开是正确方向：

```text
Tool Result → Evidence → Fact → PRD Claim
```

每层只承担一种职责，可以独立测试和审计。

### 5.2 `SUPPORTED` 不能完全由模型决定

建议 Grounding 分两阶段：

#### 确定性校验

- Evidence 的文件、行号和 Symbol 是否存在。
- `resolved_commit_sha` 是否与 Investigation 固定版本一致。
- 内容哈希是否匹配。
- Parser Fact 是否能从结构化输入直接复现。
- Fact 是否至少连接一个有效 Evidence。

#### 语义支持校验

- Evidence 是否支持 Fact 的完整陈述，而非仅主题相关。
- PRD Claim 是否超出 Fact 的范围。
- 多来源是否冲突。

第二阶段可以使用模型，但模型只输出支持等级和理由，不能覆盖第一阶段失败结果。

建议规则：

- Parser 直接生成且通过确定性校验的 Fact 可进入 `SUPPORTED`。
- 模型抽取 Fact 默认进入 `PARTIALLY_SUPPORTED`，通过语义校验后才能升级。
- `INFERRED` 永远不能自动升级为 `CODE_VERIFIED`。
- `CONFLICTING` 必须保留冲突，不由 Agent 自动选择结论。

### 5.3 Evidence 存储应最小化

M0 可以保存最小代码片段便于演示和 Eval。生产环境应限制片段长度、过滤敏感模式、加密存储并设置保留周期。

跨用户展示时再次执行授权与敏感信息检查。代码 Locator、Hash 和 Fact 可以比完整片段保留更久。

## 6. Eval 可行性与限制

### 6.1 阶段 0 优先是正确的

先建立 Direct Prompt Baseline，再增加 Single Retrieval、Bounded Loop 和 Grounding，能够判断新增复杂度是否产生真实收益。

没有 Baseline 时，团队无法知道质量提升来自调查机制、提示词变化还是模型本身。

### 6.2 Case 数量建议

- 10 个 Case：适合端到端冒烟和演示。
- 15～20 个 Case、每配置至少 3 次 Trial：适合首轮回归比较。
- 30 个以上 Case：更适合对 Information Need Precision/Recall 和冲突识别率作趋势判断。

因此文档中的“不少于 10 个”可以保留为最低验收，但 README 不应把小样本结果描述为普遍结论。

### 6.3 指标需要分为确定性和评分型

确定性指标：

- Expected Fact 命中。
- Required Evidence 命中。
- Unknown 与 Conflict 命中。
- Tool Call、重复动作、停止原因、Token 和时延。

评分型指标：

- Requirement Coverage。
- Boundary Recall。
- Acceptance Criteria Executability。
- Internal Consistency。

评分型指标应使用明确 Rubric，并抽取部分样本进行人工复核。模型 Judge 的模型版本、Prompt 版本和评分结果必须保存。

### 6.4 多次运行稳定性

每个配置至少运行多次，并记录均值、离散程度和失败轨迹。模型或 Prompt 变更后，不只比较平均分，还应检查关键 Case 是否回退。

## 7. 检索与远程代码库

### 7.1 历史 PRD 先关键词后向量

先实现关键词或全文检索是可行且正确的 Baseline。小规模资料库可以直接执行精确向量查询，无需立即建立 HNSW。

pgvector 支持精确检索和 HNSW、IVFFlat 近似索引。近似索引会引入召回与性能权衡，因此应在数据规模和评测证明需要后加入。

参考：[pgvector](https://github.com/pgvector/pgvector)

### 7.2 远程仓库优先使用临时只读 checkout

GitHub Contents API 对目录条目和文件大小存在限制，代码搜索也有独立速率限制。

参考：[GitHub Repository Contents API](https://docs.github.com/en/rest/repos/contents)、[GitHub REST Rate Limits](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api)

建议 Production Profile 的 GitHub/GitLab Adapter：

1. 使用最小权限 App Token 解析分支或 Tag 到 commit。
2. 将指定 commit 浅克隆或下载归档到隔离只读目录。
3. 使用与 M0 相同的 Native Repository Tools 调查。
4. 调查结束后按保留策略清理临时 checkout。

这样可复用本地工具、稳定绑定 commit，并减少大量零散 API 请求。

## 8. 推荐实施基线

### 8.1 技术选择

| 项目 | 推荐选择 |
| --- | --- |
| 主语言 | Python |
| Workflow | LangGraph 低层图 API |
| 数据模型 | Pydantic |
| 业务数据库 | PostgreSQL |
| ORM 与迁移 | SQLAlchemy + Alembic |
| M0 入口 | CLI |
| M1 前端 | Next.js + TypeScript |
| M1 API | FastAPI |
| Production Profile 队列 | Celery + Redis |
| 本地代码检索 | `rg` + 受限文件读取 + 确定性 Parser |
| 历史 PRD 首版 | PostgreSQL 全文检索 |
| 向量检索 | 评测证明收益后增加 pgvector |

### 8.2 实施顺序

1. 固定 Demo Repository、Ground Truth 和 Direct Prompt Baseline。
2. 实现纯领域类型、Policy 和最小 PRD Workflow。
3. 实现 Repository Tools 和确定性 Evidence。
4. 实现 Information Need、Coverage 和 Investigation Loop。
5. 实现 Fact Extractor 与两阶段 Grounding。
6. 运行 Ablation，修正预算、停止和 Coverage 策略。
7. 完成动态确认单元和整份 Markdown PRD。
8. 增加 FastAPI、Next.js 和用户可见调查轨迹。
9. 增加历史 PRD、远程仓库和飞书。
10. 最后增加 Redis、Celery、Outbox、OIDC 和生产部署。

## 9. 进入实施计划前锁定

1. M0 开始统一使用 PostgreSQL，不维护 SQLite/PostgreSQL 双实现。
2. 使用 LangGraph 低层 Graph API 和 PostgreSQL Checkpointer；业务状态与图 checkpoint 分别管理。
3. 首版仓库工具限定为目录、文本搜索、文件读取、OpenAPI、数据库 Schema 和测试查找。
4. Grounding 以确定性校验作为硬门禁，对自然语言结论增加模型语义校验。
5. 最低保留 10 个 Eval Cases，实施目标为 15～20 个，每种配置至少运行 3 次。
6. Celery 仅传递 `run_id` 并负责调度；Worker 根据 PostgreSQL 状态和 LangGraph checkpoint 幂等恢复。
7. pgvector、外部 Coding Agent 和生产级队列均不阻塞 M0；pgvector 首先使用精确检索。
8. 远程仓库通过授权接口解析到固定 commit，在隔离临时工作区建立快照，并复用本地调查工具。
9. 明确 `task_id`、`run_id`、`thread_id`、`checkpoint_id` 映射、图版本策略、幂等键和 checkpoint 保留策略。

## 10. 最终结论

这组判断已经足以进入 step plan，技术方向没有明显不可行项。

最重要的修正是：

> LangGraph 负责可恢复的图执行，不负责业务 exactly-once；Celery 负责唤醒，不负责状态；PostgreSQL 业务表仍然是用户可见业务状态的唯一事实来源。
